# Type 15 Business Rules Implementation Plan

## Goal

Add a new translation type named **15. Business Rules** for Dataverse business rule labels, especially error messages and recommendation text generated by business rule actions.

This type is entity-scoped. Implement and verify the standalone **15. Business Rules** type first. **0. All-In-One** integration is intentionally deferred and must be handled in a later work item. Types **16. Modern Commands** and **17. Entity Messages** must not be included in All-In-One.

Numbering note: standalone Business Rules now owns menu number `15`. The existing classic ribbon handler remains separate and should keep its existing implementation; its display number must not conflict with Business Rules.

## Primary Save Strategy

Use direct `workflow.xaml` label update, not solution export/import translation package.

Reasoning:

- The repo already has a precedent: `BpfHandler.js` directly updates `workflow.xaml` for BPF labels.
- Business rule labels are visible as `mcwo:StepLabel` nodes in `workflow.xaml`.
- Active workflows usually require deactivate before patching, then activate again.
- This is simpler than the ribbon solution export/import path and avoids importing a full translation package.
- Runtime code must not implement a persisted/downloaded backup flow for Business Rules. Save should behave like BPF: read current XAML, deactivate if needed, patch XAML, update workflow, reactivate if needed.
- A best-effort in-memory rollback during the same failed save is acceptable if it follows the existing BPF pattern, but there is no user-facing backup file/download in the product flow.

Fallback only:

- If direct XAML update cannot round-trip labels reliably, then use official `ExportTranslationRequest` / `ImportTranslationRequest` as a fallback.
- Do not start with export/import package for Business Rules.

## Handler Scope

Translate business-rule-owned labels for the selected entity:

- `SetMessage` error message labels.
- Recommendation title labels.
- Recommendation detail/action labels.
- Any other `mcwo:StepLabel` nodes found in business rule XAML.

Do not translate:

- Condition values like `ABCD`.
- Field names, entity names, or lookup values inside conditions/actions.
- Generated JavaScript logic.
- Non-label workflow XAML.

## Handler Design

Create `js/BusinessRuleHandler.js` with the same shape as existing handlers:

- `BusinessRuleHandler.Load()`
- `BusinessRuleHandler.Save()`
- `BusinessRuleHandler.SaveOnly()`

`Load()`:

1. Require selected solution and selected entity.
2. Query `workflow` records:
   - `category eq 2` if confirmed for Business Rules in the environment, otherwise use the observed category value from FetchXML/Web API metadata.
   - `primaryentity eq <selected entity logical name>`.
   - include active and draft rules.
3. Select:
   - `workflowid`
   - `name`
   - `statecode`
   - `statuscode`
   - `scope`
   - `clientdata`
   - `xaml`
4. Parse `workflow.xaml` for `mcwo:StepLabel` nodes.
5. Optionally parse `workflow.clientdata` to improve labels/action context.
6. Populate `XrmTranslator.metadata` with workflow XML and label maps.
7. Fill the grid with parent rows per business rule and child rows per label.

`SaveOnly()`:

1. Collect changed child rows.
2. If no changes, return a resolved promise.
3. Group changes by `workflowid`.
4. For each workflow:
   - read latest `workflow.xaml` and `workflow.clientdata`
   - deactivate when current state is active
   - patch XAML labels by `LabelId` and LCID
   - patch clientdata labels only if proof says it is required
   - update the `workflow` record
   - reactivate if it was active before save
5. Publish if required.

`Save()`:

1. Lock grid as existing handlers do.
2. Call `SaveOnly()`.
3. Reload the handler.

## No Runtime Backup

Business Rules must not copy the ribbon backup UX.

Runtime behavior:

- no backup dialog
- no backup XML download
- no backup web resource
- no repo/docs write from the browser
- direct XAML update only

Implementation may keep the original XAML in memory during a single save operation for best-effort recovery if an update fails before reactivation. That is not a persisted backup feature.

## Grid Shape

Preferred shape:

```text
Business Rule: New business rule
  Error message: This is the create by value.
  Recommendation title: Recommendation Title for Sales Order on Create On
  Recommendation detail: Make sure you enter detail Recommendation Title for Sales Order on Create On
```

Columns:

- `schemaName`: friendly label row name.
- one column per installed language, same as existing handlers.

Keep metadata off-screen on child records:

- `_isBusinessRuleLabelRow = true`
- `_businessRuleId`
- `_businessRuleName`
- `_labelId`
- `_labelKind`
- `_sourceField`
- `_originalXaml`
- `_allInOneType` when loaded through All-In-One

All language cells should be editable for child rows. Parent rows should be non-editable.

## Edge Cases

- No selected solution: block load with a clear message.
- Selected entity has no business rules: show empty state.
- Business rule has conditions but no `StepLabel` nodes: show empty child list for that rule or skip it.
- Business rule is active: automatically deactivate before save and reactivate after save.
- Business rule was already inactive: keep it inactive after save.
- Business rule save fails after deactivate: attempt best-effort in-memory restore and reactivate to original state, similar to BPF. Do not depend on a persisted backup file.
- A label exists in `clientdata` but not XAML: log/report it and do not guess until proof confirms the right write path.
- User has only one language installed: load should still work but target translation cells may not exist.
- Future All-In-One with no Business Rule rows should not fail the whole load.
